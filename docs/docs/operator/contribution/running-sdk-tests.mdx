# Running the SDK Tests

The SDK's test projects live under `test/`, one per package. Two kinds of tests exist:

- **Unit tests** run without any external dependency.
- **Integration tests** (files named `*.Integration.Test.cs`, grouped in the
  `[Collection("Integration Tests")]` xUnit collection) require a **running Kubernetes cluster**
  reachable through your current kubeconfig context. The CI uses [kind](https://kind.sigs.k8s.io/);
  locally any cluster works (kind, minikube, Docker Desktop, …). The integration tests of
  `KubeOps.Cli.Test` also need `kubectl` on the `PATH`: they run the CLI against the operator in
  `test/KubeOps.Cli.Test.Operator` and validate the generated manifests with `kubectl kustomize` and a
  server-side dry run.

:::caution
Integration tests create and delete resources (CRDs, namespaces, custom resources) in the cluster
of your **current kubeconfig context**. Only run them against a disposable development cluster.
:::

## Commands

```bash
# Run all tests (requires a cluster for the integration tests)
dotnet test

# Run tests for a specific project
dotnet test --project test/KubeOps.Operator.Test/KubeOps.Operator.Test.csproj

# Run only unit tests (skip integration tests) — no cluster required
dotnet test --project test/KubeOps.Operator.Test/KubeOps.Operator.Test.csproj \
  --filter-not-trait "Category=Integration"

# Run a single test by name
dotnet test --filter "FullyQualifiedName~MyTestClass.MyTestMethod"
```

## Webhook Integration Tests

The admission webhook integration tests in `KubeOps.Operator.Web.Test` need the Kubernetes API server to
call the test app on your machine. They are skipped unless `KUBEOPS_TEST_WEBHOOK_HOST` holds a host name or
IP address under which the API server reaches your machine. The test app then serves HTTPS on port `5443`
with a generated certificate and registers the webhooks with its CA bundle, so no tunnel is needed.

```bash
# Docker Desktop or OrbStack
KUBEOPS_TEST_WEBHOOK_HOST=host.docker.internal \
  dotnet test --project test/KubeOps.Operator.Web.Test/KubeOps.Operator.Web.Test.csproj

# kind on Linux: the gateway of the kind Docker network (this is what the CI uses)
KUBEOPS_TEST_WEBHOOK_HOST=$(docker network inspect kind \
  --format '{{range .IPAM.Config}}{{println .Gateway}}{{end}}' | grep -m1 -E '^[0-9]+(\.[0-9]+){3}$') \
  dotnet test --project test/KubeOps.Operator.Web.Test/KubeOps.Operator.Web.Test.csproj
```

Port `5443` must be free. The test app removes the `dev-validators` and `dev-mutators` webhook configurations
when it stops.

## Test Conventions

- Tests use **xUnit v3** and **FluentAssertions** (`.Should().Be(...)` style).
- Test files follow the pattern `{Subject}.Test.cs` for unit tests and
  `{Subject}.Integration.Test.cs` for tests that need a live cluster.
- Integration tests inherit `IntegrationTestBase`, override
  `ConfigureHost(HostApplicationBuilder)` to wire up the operator under test, and use
  `TestNamespaceProvider` for namespace isolation. The shared integration collection disables
  parallelization and installs the required CRDs once per run. `IntegrationTestBase` also applies
  the `Category=Integration` trait so integration tests can be excluded consistently.

When you add a feature, cover it with unit tests; if it changes the watch → queue → reconcile
behavior against a real API server, add an integration test as well.
